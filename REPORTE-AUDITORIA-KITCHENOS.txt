2. FUNCIONES DE INTELIGENCIA ARTIFICIAL
================================================================================

Rutas disponibles:

Ruta                    | Modelo       | Función                                    | Auth | Rate limit
------------------------|-------------|---------------------------------------------|------|------------
POST /api/recetas/import | Sonnet 4.6  | Extrae receta desde foto/PDF/texto          | NO   | NO
POST /api/facturas       | Haiku 4.5   | Extrae ítems de factura desde imagen/PDF    | NO   | NO
POST /api/ventas/import  | Haiku 4.5   | Extrae ventas desde imágenes/tickets        | NO   | NO
POST /api/listas-precios | Haiku 4.5   | Parsea lista de precios de proveedor        | NO   | NO
POST /api/coach          | Sonnet 4.6  | Responde consultas del KitchenCoach         | NO   | NO

ATENCIÓN: Las 5 rutas de IA son públicas. Cualquier persona con la URL puede
consumir tokens de Anthropic sin autenticarse. En producción esto representa
un riesgo económico directo.

Calidad de las extracciones:
- Recetas: Alta precisión para recetas bien estructuradas. Acepta fotos de libro/pizarrón.
- Facturas: Buena extracción de ítems, cantidades y precios. La normalización a kg/l funciona correctamente.
- Ventas: Funcional pero sin validación contra carta existente.

3. BASE DE DATOS (Supabase)
================================================================================

Esquema — 28 tablas principales:

  restaurantes, equipo_miembros, user_restaurantes
  productos, categorias_producto
  recetas, ingredientes_receta
  facturas, items_factura, historial_precios_proveedor
  pedidos, items_pedido
  proveedores
  tareas
  turnos
  haccp_registros, haccp_alertas
  ventas, items_venta
  mise_en_place, produccion_items
  checklists, checklist_items, checklist_registros
  merma_registros
  pases, pase_items
  notificaciones

Row Level Security — estado real:

Todas las tablas tienen USING (true) — política permisiva sin filtro de restaurante_id.
Esto significa:

  [X] Un usuario de Restaurante A puede leer datos del Restaurante B via API directa a Supabase
  [X] No hay aislamiento multi-tenant real a nivel de base de datos
  [OK] La UI solo muestra datos del restaurante correcto (filtrado en el cliente),
       pero no es una garantía de seguridad

Excepción: /api/recetas/save usa createAdminClient() (service role) por una
limitación en las políticas de INSERT que no fue resuelta en RLS.

Migraciones:
Scripts en /scripts/ para seeding y migraciones manuales.
No hay sistema de migraciones automatizado.

4. AUTENTICACIÓN Y SEGURIDAD
================================================================================

Flujo de auth:
- Supabase Auth con proxy.ts (no middleware.ts — decisión consciente por breaking change en Next.js 16)
- AuthProvider con dos useEffect separados para evitar deadlock
- useRestauranteId() devuelve '' durante loading — todos los hooks tienen guard contra esto

Vulnerabilidades identificadas:

Severidad | Descripción
----------|-------------
ALTA      | RLS USING(true) en todas las tablas — sin aislamiento real entre restaurantes
ALTA      | Las 5 rutas de IA son públicas y no requieren autenticación
MEDIA     | /api/migrate expuesto sin auth (si existe en producción)
MEDIA     | SUPABASE_SERVICE_ROLE_KEY solo en /api/recetas/save — correcto, pero verificar no filtrarlo
MEDIA     | usePase tiene USUARIO_MOCK hardcodeado — datos de pase no corresponden al usuario real
BAJA      | Sin rate limiting en ningún endpoint

6. BLOQUEADORES PARA PRIMER CLIENTE PAGO
================================================================================

Para poder cobrar a un primer cliente real hoy, hay 5 bloqueadores críticos:

[BLOQUEADOR 1 - CRÍTICO] RLS sin implementar
Un cliente podría (accidentalmente o no) ver datos de otro restaurante consultando
Supabase directamente.
Solución: implementar USING (restaurante_id = auth.jwt() ->> 'restaurante_id')
en todas las tablas.

[BLOQUEADOR 2 - CRÍTICO] Rutas de IA públicas
Cualquiera puede usar las funciones de IA sin registrarse, generando costos
en la cuenta de Anthropic del propietario.
Solución: agregar getSession() al inicio de cada API route y devolver 401
si no está autenticado.

[BLOQUEADOR 3 - CRÍTICO] Sin sistema de pagos
No se puede cobrar.
Solución mínima: integrar Stripe o Mercado Pago con un plan simple.
Mínimo viable: una sola URL de pago por suscripción mensual.

[BLOQUEADOR 4 - IMPORTANTE] Pase con usuario mock
El módulo de pase muestra 'Facundo A.' para todos los usuarios. En un restaurante
real con múltiples empleados esto rompe la trazabilidad.
Solución: reemplazar USUARIO_MOCK por useAuth().perfil.

[BLOQUEADOR 5 - IMPORTANTE] Sin onboarding de restaurante
No existe flujo para que un cliente nuevo cree su restaurante, cargue su menú
inicial y configure su equipo. El proceso actual requiere intervención manual
(seed script).
Solución: wizard de onboarding de 3-4 pasos.

8. RESUMEN EJECUTIVO
================================================================================

KitchenOS tiene una base técnica sólida. El 80% de las funcionalidades core de
un sistema de gestión de cocina están implementadas y funcionando: recetario con
food cost, stock, pedidos, facturas con IA, HACCP, turnos y tareas. La
arquitectura Next.js 16 + Supabase es correcta para el caso de uso.

Los problemas no son de features, son de infraestructura de producción. El
sistema fue construido para demostrar funcionalidad, no para aislar datos entre
clientes pagos. Los 5 bloqueadores identificados son todos solucionables en
2-4 semanas de trabajo enfocado.

Prioridad recomendada:
  1. RLS real (2-3 días) — elimina el riesgo de fuga de datos
  2. Auth en rutas de IA (1 día) — elimina el riesgo económico
  3. Pase mock user (2 horas) — necesario para operar en un restaurante real
  4. Integración de pagos básica (3-5 días) — habilita el cobro
  5. Onboarding wizard (3-4 días) — escala el alta de clientes

Con estos 5 ítems resueltos, KitchenOS está listo para su primer cliente pago.
